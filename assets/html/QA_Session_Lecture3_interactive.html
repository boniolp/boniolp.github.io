Q1

SSD as Storage Layer vs. SSD as Cache

SSDs can be integrated into a storage hierarchy in two fundamentally different ways:

  • Storage layer: some relations (or partitions) are permanently stored on SSD, the rest on magnetic disk.
  • Cache: all data lives on magnetic disk; the SSD transparently caches frequently accessed blocks, evicting cold blocks back to disk.

(a) You are building a system that must answer real-time queries with a guaranteed maximum response time. Which architecture do you choose, and why?

(b) You have a very large customer relation (hundreds of GB). Query logs show that a small, unpredictable subset of its blocks are hot at any given moment, while the rest are rarely touched. Which architecture works better here, and why?

(a) Real-time guaranteed latency → SSD as storage layer

When a strict response-time bound must be met, SSD as a storage layer is the right choice. The latency of any query touching an SSD-resident relation is bounded by SSD access times (tens of microseconds), which are predictable. With a cache architecture, a cache miss falls through to magnetic disk (5–10 ms seek + rotational latency), breaking the guarantee. You cannot control when a cache miss occurs, so worst-case latency is magnetic-disk latency — incompatible with real-time requirements.

(b) Large relation with unpredictable hot blocks → SSD as cache

Two problems make the storage-layer approach impractical here:

  • The relation is too large to store entirely on SSD (cost prohibitive).
  • The hot blocks shift over time and are unknown in advance, so there is no static partition to place on SSD — any fixed assignment will be wrong for future access patterns.

The SSD cache adapts automatically: recently accessed blocks are promoted to SSD regardless of which part of the relation they come from, and cold blocks are silently demoted to disk. This matches the workload dynamically without any manual data placement. The trade-off is that occasional cache misses incur magnetic-disk latency, which is acceptable here since no hard real-time bound is required.

Q2

Magnetic Disk

Some database systems configure magnetic disks so that only sectors on the outer tracks are used, leaving the inner tracks completely empty — even though this wastes a significant fraction of the disk's total capacity.

What are the potential performance benefits of this strategy? Give at least two distinct reasons.

Reason 1 — Higher data-transfer rate on outer tracks

A hard disk spins at a constant angular velocity (e.g., 7 200 RPM). Because outer tracks have a larger circumference, more sectors pass under the read/write head per unit time than on inner tracks. This means the linear density of data throughput is higher on outer tracks. Restricting data to outer tracks therefore gives a consistently higher sequential transfer rate.

Reason 2 — Reduced seek distance → lower latency

If all data lives on the outermost band of tracks, the actuator arm only ever needs to sweep across a small radial range. Seek time is proportional to the distance the arm travels; by confining it to a narrow zone, average seek time falls significantly compared to using the full disk surface. This directly reduces I/O latency.

Q3

Disk-Scheduling Algorithm

A database engineer proposes the following disk-scheduling algorithm to handle two classes of requests: system requests (issued by background processes) and user requests (issued by queries).

Proposed algorithm — Priority Proximity Scheduler (PPS):
At each scheduling step:
1. If any system request is pending, serve the system request whose target track is closest to the current head position.
2. Otherwise, serve the user request whose target track is closest to the current head position.

(a) Identify a fundamental correctness problem with this algorithm.

(b) Construct a concrete example.

(c) To fix the problem, a colleague proposes the following modification:

Proposed fix — Aging: Add a maximum waiting time $T_{\max}$. Any user request that has been waiting for longer than $T_{\max}$ is promoted to system priority and becomes eligible to be selected in step 1. Among all system requests (original and promoted), the scheduler still picks the one closest to the current head.

Is this fix solving the problem of the previous solution? If you think it is correct, justify it. If you think it is still wrong, construct a concrete counterexample.

(d) If the fix in (c) is flawed, propose a truly correct algorithm.

(a) The problem with PPS

A user request can wait indefinitely and never be served. As long as system requests keep arriving — even at a moderate rate — the scheduler always picks them first. A user request sitting in the queue is permanently skipped, no matter how long it has been waiting. From the user's perspective, their query appears to hang forever, even though the disk is busy. This is a fairness failure: one class of requests completely monopolises the disk at the expense of the other.

(b) Concrete starvation example

Head starts at track 50. One user request targets track 80. System requests keep arriving continuously near track 50:

(c) The aging fix is still wrong — counterexample

Suppose U:80 has now waited longer than $T_{\max}$ and is promoted to system priority. The scheduler now holds: promoted U:80 and a stream of new (non-promoted) system requests continuously arriving near track 50 (the current head position). At each step, the "closest to head" rule picks the new system request (distance ≈ 5 tracks) over the promoted U:80 (distance = 30 tracks). Promotion did not help: the user request is still farther from the head than every newly arriving system request, so it is still skipped indefinitely.

The root cause: promotion changes the priority class of the request, but the "closest to head" sub-rule still allows arbitrarily many nearby requests to jump ahead of it. As long as new system requests keep arriving near the head, the promoted request never wins.

(d) A truly correct fix — mandatory immediate service

The key insight is that "promote to system priority" is not enough — you must make the aged request unconditionally next. The correct modification is:

  1. If any request (system or user) has been waiting for more than $T_{\max}$, mark it as urgent. Among all urgent requests, serve the one that has been waiting the longest (FIFO among urgent requests). No other request can be served until the urgent queue is empty.
  2. If there are no urgent requests, apply the original PPS rules (system priority, then closest).

Why this works: any request becomes urgent after at most $T_{\max}$ time. Once urgent, it is served before any non-urgent request regardless of head distance. The waiting time of any request is therefore bounded by $T_{\max}$ plus the time to drain the urgent queue at the moment it joins.

Degeneration under high load. If the arrival rate is very high and $T_{\max}$ is short, many requests age into urgent simultaneously. The urgent queue then degenerates into a pure FIFO over all requests, ignoring disk head position entirely. This eliminates the seek-time optimisation that motivated the original PPS design, causing excessive head movement. A practical refinement is to apply SCAN within the urgent queue. This preserves the starvation-freedom guarantee (every request in the urgent queue is served on the current or next sweep) while recovering much of the seek-time efficiency. For most workloads, a combination of aging (to bound waiting time) and SCAN (to bound head travel) is therefore a preferred strategy.

Parity Placement

A parity block $P_i$ stores the bitwise XOR of a group of data blocks. If one disk fails, any lost data block in the group can be reconstructed: $B_{\text{lost}} = P_i \oplus B_1 \oplus B_2 \oplus \ldots$ This only works if at most one block from the group is lost.

Consider the following setup: 4 disks, data blocks $B_1$–$B_{12}$ assigned round-robin ($B_j$ → Disk $((j{-}1) \bmod 4)+1$). Parity group $i$ covers $\{B_{3i-2},\, B_{3i-1},\, B_{3i}\}$, so $P_i = B_{3i-2} \oplus B_{3i-1} \oplus B_{3i}$. An engineer assigns $P_i$ to Disk $i$ (cycling $1, 2, 3, 4, 1, \ldots$), giving the following layout:

Disk 1Disk 2Disk 3Disk 4
DataB1B2B3B4
B5B6B7B8
B9B10B11B12
ParityP1P2P3P4

(a) Is this arrangement robust to disk failure?

(b) If not, propose a corrected placement formula and the resulting layout.

(a) The flaw — Group 1 as example

Group 1 = $\{B_1, B_2, B_3\}$ with $P_1 = B_1 \oplus B_2 \oplus B_3$. From the round-robin rule: $B_1$ → Disk 1, $B_2$ → Disk 2, $B_3$ → Disk 3. The engineer places $P_1$ on Disk 1 (since $i=1$).

Both $B_1$ and $P_1$ are on Disk 1. If Disk 1 fails, we lose $B_1$ and $P_1$ simultaneously. The surviving blocks are $B_2$ (Disk 2) and $B_3$ (Disk 3), but reconstruction requires the parity: $B_1 = P_1 \oplus B_2 \oplus B_3$. Since $P_1$ is also gone, $B_1$ cannot be recovered.

The same pattern repeats: Group 2 = $\{B_4, B_5, B_6\}$. $B_6$ → Disk $((6{-}1) \bmod 4)+1$ = Disk 2. $P_2$ is also on Disk 2. If Disk 2 fails, $B_6$ and $P_2$ are both lost, making $B_6$ unrecoverable. Every group has one such co-location conflict.

(b) Corrected placement

The parity block for group $i$ must go to the one disk that holds none of $B_{3i-2}$, $B_{3i-1}$, $B_{3i}$. Because data is round-robin across 4 disks, each group of 3 data blocks occupies exactly 3 of the 4 disks, leaving exactly one disk free per group:

  • Group 1: $B_1$(D1), $B_2$(D2), $B_3$(D3) → free disk = D4 → $P_1$ on D4
  • Group 2: $B_4$(D4), $B_5$(D1), $B_6$(D2) → free disk = D3 → $P_2$ on D3
  • Group 3: $B_7$(D3), $B_8$(D4), $B_9$(D1) → free disk = D2 → $P_3$ on D2
  • Group 4: $B_{10}$(D2), $B_{11}$(D3), $B_{12}$(D4) → free disk = D1 → $P_4$ on D1

The general formula for $D=4$ disks: $\text{Disk of } P_i = ((D - i) \bmod D) + 1 = ((4 - i) \bmod 4) + 1$. The parity rotates in the direction opposite to the data, ensuring no disk in the cycle holds both $P_i$ and any of its data blocks.

Disk 1Disk 2Disk 3Disk 4
DataB1B2B3B4
B5B6B7B8
B9B10B11B12
ParityP4P3P2P1

Verification — Disk 1 failure: lose $B_1$, $B_5$, $B_9$, $P_4$. For Group 1: $P_1$(D4) and $B_2$(D2), $B_3$(D3) all survive → reconstruct $B_1 = P_1 \oplus B_2 \oplus B_3$ ✓. For Group 4: $P_4$ is lost, but Group 4 = $\{B_{10}, B_{11}, B_{12}\}$ are on D2, D3, D4 — none lost — no reconstruction needed ✓. Any single-disk failure destroys at most one data block per group (its parity is on a different disk) and possibly one parity (whose data blocks are all intact). Recovery is always possible.

Q5

Slotted Pages and the Free-Space Map

A file consists of 3 slotted pages (P1, P2, P3), each 400 bytes. A page header costs 8 bytes; each slot entry costs 4 bytes. Records are packed from the right. When a new record must be inserted, the system always picks the page with the most contiguous free space (as reported by the FSM). Ccompaction is not run automatically.

Starting from three empty pages, execute the following sequence:

  1. INSERT r1 (70 B), r2 (50 B), r3 (90 B), r4 (60 B), r5 (80 B)
  2. DELETE r2
  3. INSERT r6 (55 B)
  4. DELETE r4
  5. INSERT r7 (75 B)

(a) After the full sequence, for each page state: the total free bytes, whether the free space is contiguous, and the largest single record that can be inserted.

(b) We maintain a free-space map (FSM) with only $2n$ bits total for $n$ pages (2 bits per page). How do you encode the free space of each page? What precision does this give you?

(c) With $k$ bits per page and a page of size $B$ bytes, what is the granularity of the free-space estimate? Give the formula.

(d) What is the benefit and the drawback of using a small $k$ (e.g., $k=2$) compared to a large $k$?

Model: what "contiguous free" means

In a slotted page, the slot directory grows left→right from the header; records are packed right→left from the page end. Contiguous free = distance between the end of the last slot entry and the start of the leftmost live record. Each INSERT costs 4 B (new slot) + record size; each DELETE nulls the slot without shrinking the directory. A hole is visible to the FSM only if deleting a record moves the leftmost-live-record pointer (i.e., the deleted record directly bordered the free zone). Otherwise the hole is invisible to the FSM and cannot be used without VACUUM.

Initial state: all pages empty, slot_dir_end = 8 B (header only), contiguous = 392 B each.

INSERT r1 (70 B) → all tied (392 B). Use P1. P1: slot_dir_end=12, leftmost_live at 330. Contiguous = 318 B. P1=318, P2=392, P3=392.

INSERT r2 (50 B) → P2 or P3 tied (392 B). Use P2. P2: 338 B. P1=318, P2=338, P3=392.

INSERT r3 (90 B) → P3 (392 B). P3: 298 B. P1=318, P2=338, P3=298.

INSERT r4 (60 B) → P2 (338 B). P2: 274 B. Layout: [hdr][slot_r2][slot_r4]…[274 B free]…[r4=60 B][r2=50 B]. P1=318, P2=274, P3=298.

INSERT r5 (80 B) → P1 (318 B). P1: 234 B. P1=234, P2=274, P3=298.

DELETE r2 (on P2, at far-right, 50 B): slot nulled. r4 is still live and directly borders the free zone. The 50 B hole is on the far right, not adjacent to the free zone. FSM is not updated. P2 contiguous = 274 B (unchanged).

INSERT r6 (55 B) → P3 (298 B, most contiguous). P3: 298−59 = 239 B. P1=234, P2=274, P3=239.

DELETE r4 (on P2, the leftmost live record, bordering the free zone, 60 B): slot nulled. Now there are no live records on P2. The leftmost-live-record pointer moves to the end of the page. Both the old free zone (274 B) and the two former record spaces (60 B + 50 B) merge into one contiguous region. P2 contiguous = 400 − 8 (hdr) − 8 (2 null slots × 4 B) = 384 B. The FSM updates to reflect this.

INSERT r7 (75 B) → P2 (384 B, now the most contiguous). P2: 384−79 = 305 B. P1=234, P2=305, P3=239.

(a) Final state

PageRecordsSlot dirContiguous freeHolesLargest insertable (no VACUUM)
P1r1, r52 live234 BNone230 B
P2r72 null + 1 live305 BNone301 B
P3r3, r62 live239 BNone235 B

No page has any holes at the end. P2 recovered all its fragmented space when r4 (the last live record) was deleted — the FSM correctly reflected this, routing r7 there. Contrast this with a total-free FSM: it would have sent r6 to P2 (because 274+50=324 > 298), creating a hole on P2, and the FSM would never have noticed the self-healing at DELETE r4.

(b) 2 bits per page encoding

With 2 bits we can represent $2^2 = 4$ states. A natural encoding divides the contiguous free space into quartiles of the page capacity:

  • 00 → 0–25% contiguous free (nearly full)
  • 01 → 25–50% contiguous free
  • 10 → 50–75% contiguous free
  • 11 → 75–100% contiguous free (mostly empty)

Precision: we only know which quarter the contiguous free space falls in, not the exact byte count.

(c) Granularity formula

With $k$ bits, there are $2^k$ levels. The granularity (size of each band) is:

$$\text{granularity} = \frac{B}{2^k} \text{ bytes}$$

For $k=2$, $B=8\,192$: granularity $= 8192/4 = \mathbf{2\,048}$ bytes. The FSM can only tell us the free space within a 2 KB window.

(d) Small $k$ vs. large $k$

Benefits of small $k$: the FSM occupies very little space (for $n$ pages, only $k \cdot n$ bits). More importantly, many inserts and deletes do not cross a quartile boundary, so the FSM rarely needs to be updated — reducing write overhead on the FSM itself.

Drawback of small $k$: the free-space estimate is coarse. A page might be skipped because it falls below a quartile threshold even though it has just enough space. Both effects cause either wasted I/O or suboptimal space utilisation.

Q6

Buffer Pool Replacement — LRU vs. MRU

Background. A buffer pool is a fixed set of memory frames that cache disk blocks. When a block is requested:

  • Hit: the block is already in a frame — it is returned immediately (no disk I/O).
  • Miss: the block is not in any frame — it must be read from disk. If all frames are occupied, one must be evicted (written back to disk if dirty, then its frame reused).

Two replacement policies decide which frame to evict on a miss:

  • LRU (Least Recently Used): evict the block that was last accessed furthest in the past.
  • MRU (Most Recently Used): evict the block that was last accessed most recently.

The buffer pool has 4 frames. All frames start empty. Blocks are referenced in this order (each number is a block ID):

1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5

Why MRU beats LRU here

After scanning the inner relation (s1→s2→s3), the last page accessed is s3 — the page least likely to be needed at the start of the next inner scan. MRU evicts s3 first (and s2 before it, during the scan), keeping s1 in the buffer. When the second iteration of the inner loop begins with s1, it is a cache hit.

LRU does the opposite: it keeps s3 (most recently accessed) and evicts s1 (least recently accessed) — exactly the page that will be needed first next time. This is why LRU thrashes completely on repeated sequential scans, while MRU naturally keeps the "head" of each scan in the buffer for reuse.

The general rule: MRU is better when the same sequence is scanned repeatedly (nested-loop join, repeated table scans). LRU is better when recent accesses predict future accesses (point queries, random access workloads).

Three Buffer-Write Strategies

A buffer (in RAM) sits between the application and the disk. Below are three strategies for handling READ and WRITE operations.

StrategyOn READOn WRITE
AIf block in buffer → return it. Else load from disk into buffer, return.Write directly to disk.
BIf block in buffer → return it. Else load from disk into buffer, return.If block is in buffer → update buffer. If not in buffer → write to disk.
CCheck disk to verify buffer copy is up-to-date. Return up-to-date copy.Write directly to disk.

(a) Evaluate each strategy on three dimensions: read latency, write consistency, and durability. Which strategy is best overall, and why?

(b) Does a better strategy exist?

Strategy A correctness problem

Suppose block B is loaded into the buffer during a read, then a write updates block B's content on disk (bypassing the buffer). The buffer now holds a stale copy of B. The next read for B finds it in the buffer and returns the old value — the application silently reads outdated data. Example:

  1. READ B → buffer loads B (value = 42), returns 42. ✓
  2. WRITE B = 99 → written to disk only. Buffer still holds B = 42.
  3. READ B → buffer hit, returns 42. ✗ (correct answer is 99)

(a) Strategy comparison

StrategyRead latencyWrite consistencyDurability on crash
AFast (buffer hits)❌ Stale reads after writes✓ (writes go straight to disk)
BFast (buffer hits)✓ (buffer updated on write)❌ Some writes not on disk
C❌ Slow (disk check on every read)✓✓

(b) A new Strategy D's

The solution is to fix Strategy B by writing to disk directly after updating the buffer.

StrategyOn READOn WRITE
DIf block in buffer → return it. Else load from disk into buffer, return.If block is in buffer → update buffer, then disk. If not in buffer → write to disk.

Strategy D's durability risk and the WAL fix

Strategy B writes data to the disk file on every write, which is good for durability. However, if the database needs to group writes (to amortise disk I/O), it may buffer multiple writes before flushing — at which point the unflushed data is lost on a crash.

Real systems use a Write-Ahead Log (WAL): every write is first recorded sequentially in a log file on disk before the actual data page is modified. On crash recovery, the system replays the log to restore any changes that hadn't reached the data pages yet. The log is written sequentially (very fast), so read performance through the buffer is preserved while durability is guaranteed by the log.

Multitable Clustering — Design and Trade-offs

Consider two relations:

  • Student(sid CHAR(5), sname VARCHAR(15), dept CHAR(10)) — average record size 30 bytes
  • Enrollment(sid CHAR(5), course_id CHAR(8), grade CHAR(2)) — average record size 15 bytes

2 — Block count

Separate files: Student: $\lceil 6000\times30/4096\rceil = 44$ blocks. Enrollment: $\lceil 30000\times15/4096\rceil = 110$ blocks. Total: 154 blocks.

Clustered file: one group = 30 + 5×15 = 105 B; groups per block = $\lfloor 4096/105\rfloor = 39$; blocks = $\lceil 6000/39\rceil =$ 154 blocks. Same total — the gain is in I/O pattern for joins, not storage size.

3 — Why the Student-only scan is slower

Separate Student file: 44 blocks, containing only student records — 180 KB read to scan all students.

Clustered file: the 154 blocks interleave student and enrollment records. A scan for dept='CS' must read all 154 blocks (632 KB) and discard the 5× more enrollment records that are irrelevant. Extra I/O: $154 - 44 = 110$ extra blocks ≈ 451 KB of unnecessary data.

The join produces 1 200 CS students × 5 enrollments = 6 000 result rows.

Separate files — nested-loop join (no index):

For each page of Student (outer, 44 blocks), scan all pages of Enrollment (inner, 110 blocks). Cost = $44 + 44 \times 110 = 44 + 4\,840 = \mathbf{4\,884}$ block reads (44 for the first full scan of Student, then 110 Enrollment blocks re-read for each of the 44 Student pages).

Clustered file — single sequential scan:

The clustered file is scanned once: 154 blocks. Each student record is immediately followed by its enrollment records in the same (or adjacent) block. The join result is assembled on the fly, with no second pass and no random I/O. Cost = 154 blocks.

Wear Leveling

An SSD has 8 physical cells $C_0$–$C_7$, each tolerating at most $W_{\max} = 10$ writes before becoming unreliable. Let $w_j(t)$ denote the number of writes to cell $C_j$ after $t$ operations. The system stores 4 logical variables (X, Y, Z, W). A program executes the following sequence of 20 operations:

W(X), W(Y), W(X), W(Z), W(X), W(Y), W(X), W(W),
W(X), W(Z), W(X), W(Y), W(X), W(W), W(X), W(Z),
W(X), W(Y), W(X), W(W)

Define the SSD lifespan at time $t$ as the number of additional write operations that can be performed before any cell fails:

$$\text{Lifespan}(t) = \min_{j \in \{0,\ldots,7\}} \bigl(W_{\max} - w_j(t)\bigr)$$

The objective of a wear-leveling strategy is to maximise $\text{Lifespan}(t)$ for all $t$, i.e., keep all cells as equally worn as possible so that the minimum remaining capacity is as large as possible.

(a) First approach: logical address = physical address (X→$C_0$, Y→$C_1$, Z→$C_2$, W→$C_3$; $C_4$–$C_7$ unused). Compute $w_j(20)$ for each cell. What is $\text{Lifespan}(20)$? After how many operations does the SSD fail?

(b) Propose a better mapping strategy. Describe it in plain terms.

(c) Is there any residual problem when some variables are written much more frequently than others?

(a) Naive approach — write counts and lifespan

Count writes per variable in the 20-operation sequence: X appears 10 times, Y appears 4 times, Z appears 3 times, W appears 3 times. Total: 20 writes.

$$\text{Lifespan}(20) = \min(0,\,6,\,7,\,7,\,10,\,10,\,10,\,10) = \mathbf{0}$$

The SSD effectively fails after operation 19 (the 10th write to X, making $C_0$ worn out). At that point, 60 write-slots remain across $C_1$–$C_3$ and 40 more across $C_4$–$C_7$. A total of 80 out of 100 available write-slots were never used.

(b) Better mapping — dynamic address translation

Introduce an indirection table (Flash Translation Layer): instead of mapping X always to $C_0$, the table dynamically routes each write of variable X to whichever physical cell has been written the fewest times so far. The procedure:

  1. On a write to variable $v$: scan all 8 cells, find $C^* = \arg\min_j w_j(t)$.
  2. Write $v$'s new value to $C^*$.
  3. Update the table: $v \mapsto C^*$. Mark the previous cell holding $v$ as free (its data is now stale).

Ideal lifespan with perfect distribution: 20 writes spread evenly across 8 cells = 2.5 writes per cell on average. Since write counts must be integers, the best possible outcome is some cells at 3 and some at 2, giving $\min_j(10 - w_j) \geq 10 - 3 = 7$. In practice, $\text{Lifespan}(20) = 7$ with an optimal strategy — compared to 0 with the naive approach.

Why naive fails: because X is always written to $C_0$, $w_0$ reaches $W_{\max}$ long before any other cell is close to its limit. The naïve approach cannot redistribute writes from a "hot" variable across multiple cells.

(c) Residual problem — static data blocking fresh cells

With dynamic translation, X's writes are spread across many cells. But Y, Z, W are written infrequently, so the cells holding their current values are rarely replaced — they stay resident with low $w_j$ counts. Since those cells hold valid (live) data, they cannot be used as write targets for X. As the sequence progresses, X exhausts the remaining "free" cells (those not holding live static data), and we see:

$$\text{Lifespan}(t) = \min\bigl(\underbrace{W_{\max} - w_{j_{\text{hot}}}(t)}_{\text{X's cells, wearing fast}},\; \underbrace{W_{\max} - w_{j_{\text{cold}}}(t)}_{\text{Y/Z/W cells, nearly 0}}\bigr)$$

The minimum is determined by the most written cells (X's), and the cold cells never contribute their capacity.

Further improvement — static wear leveling: periodically, even when no write is pending for Y, Z, or W, the system proactively migrates their values from low-wear cells to high-wear cells (that are still within limits), freeing the low-wear cells for X's next writes. This forces all cells to age at roughly the same rate. The cost is extra write operations for migration, but $\text{Lifespan}(t)$ is maximised by keeping $\max_j w_j(t) - \min_j w_j(t)$ small.
